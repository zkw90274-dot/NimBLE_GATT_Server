# 文档分层约定（渐进式披露）

> 上级索引：[../CLAUDE.md](../CLAUDE.md)
> 本文规定 `CLAUDE.md` 与 `docs/*.md` **各自放什么、不放什么**，以及改动组件时文档怎么跟着走。
> 给人看，也给 agent 看：冷启动只需要读 L0（`CLAUDE.md`，不到 90 行），要动哪个组件再展开对应那一份 L1。
> 全套文档加起来一千多行，全塞进上下文是浪费。

---

## 1. 一句话

**索引薄、正文分层、一条事实只有一个权威出处。** 复制是腐烂的开始：两处各改一半，第三天就没人知道哪份是真的。

---

## 2. 三层结构

| 层 | 位置 | 只放这些 | 一律不放 |
|---|---|---|---|
| **L0** | `CLAUDE.md` | 项目一句话、当前状态、文档地图、速查表（引脚/版本/命令）、**跨组件**的坑、目录树顶层 | 任何单组件的实现细节、算法推导、协议字段表、排错长文 |
| **L1** | `docs/<组件>.md` | 该组件的职责、关键路径、数据流、配置常量、坑、**验收怎么做** | 别的组件的内部实现（用链接指过去） |
| **L2** | 代码内注释 | 为什么这么写：隐藏的约束、微妙的不变量、某个 workaround 对应的具体 bug | 代码本身已经说明的东西、当前任务的来龙去脉（那属于 PR 描述） |

判据：**这条信息会不会因为改另一个组件而失效？** 会 → 它是跨组件事实，留在 L0 的坑列表；不会 → 下沉到 L1。

---

## 3. 归属表与禁止复制清单

本项目当前的权威分工。改任何一条，只改"权威出处"那一列。

| 事实 | 权威出处 | 其它文档怎么引用 |
|---|---|---|
| 12 字节报文布局、UUID、设备名、**线上观测到的**通知速率（18–20 Hz、50/55 ms 抖动） | `docs/host-integration.md` §2 | 只写「见 host-integration §2」，**不要**再抄一遍字段表 |
| GATT 服务端代码结构、订阅回调 | `docs/ble-interface.md` | 同上 |
| 固件侧限速常量 `CONFIG_IMU_NOTIFY_PERIOD_MS` 与采样/降级逻辑 | `docs/imu.md` | 引用时写「名义 20 Hz」，具体数值以 imu.md 为准 |
| IMU 驱动、姿态解算、零偏漂移 | `docs/imu.md` | 引用结论（如「yaw 相对开机、会漂」）时带链接 |
| 上位机选型、流水线、UI 验收、发布 | `docs/host-app.md` | 同上 |
| 构建/烧录/分区表的坑 | `docs/build-and-flash.md` | L0 只留一句话 + 链接 |

**禁止复制清单**（历史上真的出现过两份的情况）：

- 协议字段表 / 字节序 / 范围
- 「线上速率是多少」这类实测结论（≠ 固件常量，两者分属上面两行）
- yaw 是否绝对方位
- 引脚分配：**数值**允许在 L0 速查表出现一次（这是唯一的重复豁免，因为它需要一眼看到），但**为什么是这个脚、配错会怎样**只在 L1 讲。L1 里那张带 Kconfig 符号的表是权威，L0 只是抄送

## 4. L1 组件文档的骨架

新文档照这个顺序写，读者可以只看前两节就走：

```markdown
# <组件> —— 一句话定位

> 上级索引：../CLAUDE.md
> 相关：xxx.md（职责边界说明）

## 0. 一句话概括        ← 30 秒读者到此为止
## 1. 需求边界（已确认）  ← 决定过的事 + 决定不做的事
## 2. 架构 / 数据流      ← 图 + 取舍表，不写逐行说明
## 3. 已完成 vs 未完成    ← 如实，含"仅编译通过、未真机实测"这类限定
## 4. 复现步骤           ← 可直接粘贴执行的命令
## 5. 验收怎么做         ← 判据 + 自动化脚本入口
## 6. 坑               ← 编号，写现象 + 根因 + 解法
```

**写法要求**：

- 状态用 ✅ / **未做** / 「仅编译通过，未实测」三档如实标注，不要用「基本完成」。
- 每个结论带证据：实测数字、命令输出、日期。例：`100 Hz 实测到达 99.6–100.1 Hz、丢帧 0（2026-09-23）`。
- 坑必须编号，别处引用时用「§6.7」这种可寻址形式。
- 表格优于长段落；代码块只放**实际执行过的**命令。

---

## 5. 新增 / 修改组件时做什么

新增组件：

- [ ] 建 `docs/<组件名>.md`，套 §4 骨架
- [ ] 在 `CLAUDE.md` 文档地图加一行（内容 + **什么时候读**）
- [ ] 检查是否与既有文档抢同一事实，抢了就在 §3 归属表里判给一方，另一方改成链接
- [ ] 目录树 L0 只加顶层一行，细节留在 L1

修改组件：

- [ ] 改对应那份 L1，**不要**顺手把细节搬进 L0
- [ ] 改了权威事实（协议/常量/引脚）→ 全局搜一遍旧值，确认没有第二处残留
- [ ] 新踩的坑进对应文档 §6；只有"改 A 会莫名弄坏 B"这种才升级到 L0
- [ ] 文档里的实测数字过期就改或删，宁缺毋滥

## 6. 反例 → 正例

**反例**：同一段字段表在两份文档里各存一份（改了 BLE 侧，忘了改另一份）

```markdown
# docs/ble-interface.md
### 载荷格式
固定 12 字节，3 个小端 float32 …（完整字段表）

# docs/host-integration.md
### 载荷格式
固定 12 字节，3 个小端 float32 …（又抄了一遍）
```

**正例**：一份权威，一份指路

```markdown
# docs/host-integration.md      ← 唯一权威定义
### 载荷格式
（完整字段表）

# docs/ble-interface.md         ← 只指路，然后讲服务端自己的实现
### 载荷格式
👉 见 host-integration.md §2
服务端侧实现要点：
- 序列化在 gatt_svc.c 的 imu_attitude_to_le()
- put_f32_le() 用 memcpy 搬 float 的位模式，不是数值转换
```

**反例**（L0 膨胀）：把「ScottPlot 图内文字不支持中文」「DispatcherTimer 会量化到 15.6 ms」写进 `CLAUDE.md`。
**正例**：这类只影响单个组件的坑留在 `docs/host-app.md` §6；L0 只保留「改 `host/` 前先看 host-app.md §6」。

## 7. 什么时候该拆

出现下面任一条，就把 L1 拆成两份：

- 单份超过约 400 行，或读者一次只需要其中一节 → 按读者角色拆（本项目就是这么分出 `host-integration.md` 面向客户端、`ble-interface.md` 面向服务端维护者的）
- 一份文档同时描述「怎么做决定」和「怎么执行」→ 决策与复现分离
- 某节被其它文档反复整段引用 → 它应该独立成文

拆完必须：更新 `CLAUDE.md` 文档地图，并在被拆空的原文处留一行指路。

## 8. 自检（防腐烂）

```bash
# 同一条事实是否出现在多处：抽几个关键词全局搜
grep -rn "float32" docs/ CLAUDE.md
grep -rn "IMU_NOTIFY_PERIOD" docs/ CLAUDE.md
# L0 是否膨胀（超过 ~110 行就该往下沉）
wc -l CLAUDE.md
```

判读：某个关键词只应命中它的权威出处 + 少量「见 xxx」式引用行；命中成段的字段表或代码说明，就是复制了。
（本文 §6 的反例代码块会被自己的 grep 命中，属预期，判读时排除 `docs-convention.md`。）
